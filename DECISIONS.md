| 11 | Judge `overall` is **recomputed** from the criterion scores; the model's own arithmetic is discarded | Cheap determinism. A judge that miscounts its own weighted mean would silently distort every comparison. |
| 12 | Automatic caps (`JUDGE_AGENT.md` §3) are applied in **our** code, not requested from the judge | Same reason: a cap that the model can forget to apply is not a cap. |

## 2026-09-27 — lane 3 (F8 quotas and cost logging, F12 admin dashboard)

| # | Decision | Why |
|---|---|---|
| 26 | The quota day boundary is computed with `Intl.DateTimeFormat`, not a date library or an offset table. | `usageDateFor(tz, at)` formats the instant in the family's zone; `nextLocalMidnight` solves for the offset in effect *at the target local time* (two passes), which is what makes DST-transition days come out right. No dependency, and it cannot go stale when a government moves a DST boundary. |
| 27 | An unknown `families.timezone` falls back to **UTC with a warning**, never an error. | A bad timezone string must not be the reason a child does not get a bedtime story. The column is free text with a `'UTC'` default, so a typo is a plausible production state. |
| 28 | The daily quota increment lives in a Postgres function, `consume_daily_quota(family, date, limit)`, revoked from `anon` and `authenticated`. | `insert ... on conflict do update set count = count + 1 where count < limit` makes the increment and the limit check one atomic statement, so two racing requests at count = 2 cannot both become 3. PostgREST's `upsert` cannot express `count = count + 1`, so a function it is. Revoking execute closes the second way a client could move its own quota (RLS already blocks the first). |
| 29 | `DAILY_BUDGET_USD` is a **global cap measured over the database day (UTC)**, not per family and not per family timezone. | It bounds the owner's bill, and there is no single family whose timezone a global cap could key off. Spend comes from the `v_budget_today` view, never an in-process counter — a counter would reset on every cold start and disagree between lambdas. |
| 30 | `GENERATION_ENABLED` and `DAILY_BUDGET_USD` are read from `process.env` on **every call**, not from the cached `serverEnv()` snapshot. | F8 AC: "take effect without a deploy". Caveat worth stating plainly: on Vercel, changing an env var still needs a redeploy before the running function sees it, so the switch is only as live as the platform makes it. The code is not the limiting factor. |
| 31 | `GENERATION_ENABLED` **fails safe (on)** when the value does not parse; `DAILY_BUDGET_USD` falls back to $5. | A typo in an env var must not silently take the product down. An operator deliberately turning generation off will write a value that parses. |
| 32 | A `generation_logs` insert failure is **logged and swallowed**, never thrown. | `callModel()` awaits the sink from inside its own catch block, so a throwing sink would replace the real `ModelCallError` and lose the cause of the failure. A story that generated but was not logged beats a story that failed because logging did. The miss is loud on stderr and counted in `SupabaseLogSink.failedWrites`. |
| 33 | Migration `20260927000005` **revokes the admin views from `anon` and `authenticated`** and sets `security_invoker = on` on all of them. | The F12 views were world-readable: they are owned by `postgres`, so they bypassed RLS on `generation_logs`, and the public schema's default grants gave every client SELECT. `curl` with the anon key returned the day's spend. The dashboard reads with the service role, so revoking costs the app nothing. `v_top_topics` stays readable by `authenticated` — F10 sources its suggested-topic chips from it — but with `security_invoker` so `fact_packs`' own `status = 'ready'` policy applies. |
| 34 | The dashboard's headline median comes from a **new** `v_story_cost_summary`, which excludes stories with no log rows. | `v_cost_summary` left-joins `generation_logs`, so a story row written without logs (a seed, a fixture, another lane's test) enters the distribution at $0 and drags the median down. Both numbers are shown so the gap is visible. The existing view is untouched — it is applied elsewhere. |
| 35 | Cost per story is attributed to a writing model through `v_story_writer` (the most expensive `write`/`rewrite` row on the story), and every model is judged against **its own** expected median. | Haiku 4.5 tokenizes ~30% shorter than Sonnet 5 / Opus 5.5 / Fable 5.1 for identical text, so any cross-model comparison has to reconcile against measured tokens. Judging all models against one expected figure would label Haiku "below band" and Fable "above band" for ever. |
| 36 | `lib/costs/expected.ts` derives the expected cost per story from the §5 token table and `config/pricing.json`; no dollar figure is hard-coded. | It is the yardstick /admin compares the measured median against, so it has to move when a price moves. Confirmed against the four medians in the lane brief: $0.0445 Haiku 4.5, $0.0714 Sonnet 5, $0.1244 Opus 5.5, $0.2836 Fable 5.1. |
| 37 | The "~70% output tokens" figure is the **write call's** output share for the configured Sonnet 5 writer, and is not a constant across models. | Measured from the §5 table: all-output share runs 66% (Haiku) → 76% (Sonnet 5) → 84% (Opus 5.5) → 90% (Fable 5.1), because the input-heavy helper calls stay on Haiku whatever the writer is. Sonnet's write-output share is 70.1%, which is where the figure comes from. Nothing in the codebase should treat 70% as universal. |
| 38 | Limit refusal copy lives in `lib/limits/messages.ts`, not `config/guardrails/messages.json`. | Quota, kill switch and budget are capacity and cost limits, not guardrail refusals. If lane 5's file grows keys for these three, that file wins and these become the fallback. |
| 39 | `instrumentation.ts` installs the Supabase log sink at server boot. | One place, so no call site can forget, and it runs before any route. Guarded to the Node.js runtime — the Edge runtime has no service-role client. |
## 2026-09-27 — lane 5 (F13 eval harness, F14 bake-off)

| # | Decision | Why |
|---|---|---|
| 40 | The judge prompt is `prompts/judge.v1.md`, with everything sent to the model placed **after a `--- PROMPT ---` marker**; the text above it is editor notes and is stripped. Its sha256 is recorded in every results file. | CLAUDE.md rule 5 requires a re-run when the prompt changes. A hash in the results is how a reviewer can tell that it did, and the marker lets the file carry "never name a model in here" warnings that would otherwise become a blindness leak. |
| 41 | ~~`lib/eval/judge.ts` extends `JudgeScore` with `best_moment`/`worst_moment` locally~~ **Superseded by the lead:** both fields are now optional on `JudgeScore` in `lib/schemas/judge.ts`. | §6's report requires "three verbatim excerpts per contestant chosen by the judge as best moment and worst moment", and `JudgeScore` has no field for them. Extending keeps the cross-lane contract untouched; both fields default to empty so an older recorded fixture still parses. |
| 42 | The five sabotage/pairwise calibration rows are checked against the judge's **raw** criterion scores, before our automatic caps. | Our caps could satisfy three of those rows by arithmetic alone (a padded story is long, an unsourced fact is unsourced). A calibration row that passes because of our own code measures our code, not the judge. The capped scores are recorded alongside, never checked. |
| 43 | Blindness is asserted on the assembled payload of **every** judge call in normal operation, not only in tests, and it throws rather than warns. | §2 is the foundation of the whole bake-off: if the judge can tell who wrote a story, every pairwise verdict is contaminated. The known cost is a false positive on an ordinary word that contains a brand name — a story about fables, or about haiku. That fails the run loudly with the offending excerpt, which is the right trade; a check that can be ignored is not a check. |
| 44 | Two of §6's four "difficulty" scenarios name a topic and band that an F13 scenario already covers (`history-of-video-games`, `the-titanic` for band B). Each is kept but **differentiated by the thing that makes it harder**: the legend moves to band B, and the titanic scenario gains a series bible. | §6 says "the 8 from F13 plus 4 more", so there must be 12. Running two of them verbatim twice would add cost and no information. |
| 45 | The judge scores a looser `JudgeableStory` shape (`lib/eval/types.ts`), not `StoryOutput`. **Partly superseded:** all four references now validate against `StoryOutput` after the cold-open fold fix (#54), so the looseness is no longer required for them — kept only as tolerance for judging a story that fails the strict schema. | Two of the four references carry 11 headed sections (cold open + 9 stops + coda) and do not validate against `StoryOutput`'s 10-chapter cap — decision #25 already allows this. Scoring the calibration set through the strict schema would throw on half of it. The gate keeps the strict shape. |
| 46 | `lib/eval/references.ts` folds the cold open back into `chapters[0].text`. | `asStoryOutput()` drops `parsed.coldOpen` entirely, which loses 110 words of the LEGO story and 259 of the shark story and makes the judge score an opening that starts at "Chapter 1". | 47 | With no fact pack, the `unsourced_fact` check is recorded as `factSourcing: 'unverifiable_no_fact_pack'` — never as passed. | Decision #22: the references carry synthetic fact ids. Running the id check against them would "pass" every time while testing nothing. The eval, bake-off and calibration JSON all carry the field so a green is never misread. |
| 48 | The bake-off runs an **extra pairwise pass against the top-scoring contestant** by default (`--no-pairwise-vs-best` to skip). | §6's decision rule is stated as "loss rate against the best contestant", but step 4 only compares against the baseline. Without the extra pass the headline rule cannot be computed from the data, only estimated — and the report says so when the flag is off. |

| 50 | A `judge_error` in **either** order of a pairwise comparison collapses it to TIE. | One successful order on its own is exactly the position bias the swap protocol exists to remove, so a half-completed comparison must not be allowed to stand as a verdict. |

It is the one number in the report that will move once real families use the product; the report says to re-derive it from `stories` grouped by `series_id` after launch. |
| 52 | `pnpm eval` and `pnpm bakeoff` print a cost estimate from `config/pricing.json` before any call and **refuse a live run above $20** unless `--budget=<approved amount>` is passed. | CLAUDE.md makes spend above ~$20 the owner's decision, and the owner needs the number to make it. A refusal that names the figure and the cheaper shapes is more useful than a warning nobody reads. |
| 53 | Story generation sits behind a narrow `StoryPipeline` interface (`lib/eval/pipeline.ts`) with two implementations: lane 2's `lib/generate` `createEvalPipeline()`, loaded through a non-literal specifier, and a synthetic one. | F13 depends on F6/F7, which are in flight. The seam let the judge, the caps, the calibration checker and the report be built and tested end to end without blocking, and without importing a module that does not exist yet. Every synthetic artifact is stamped `synthetic: true` and the report opens with "THIS IS NOT A BAKE-OFF RESULT". |
## 2026-09-27 — F15 guardrails (lane 6)

| # | Decision | Why |
|---|---|---|
| 60 | The L1 hard blocklist carries the **action, not the noun**: "make a bomb" is a term, bare "bomb" is not. Likewise "nazi", "hitler", "holocaust", "massacre", "terrorism", "slavery" and "dynamite" are deliberately absent from L1. | Every one of those is a real educational topic for an older band ("the atomic bomb", "how the Second World War started", "who invented dynamite"), and GUARDRAILS.md §3.3 puts wars and historical injustice under *allow_with_care*, not refuse. A hard L1 refusal on a history word is a false refusal a parent notices immediately, and §1.1 says each layer is allowed to be imperfect because the others catch what it misses. The semantic call is L2's. |
| 61 | Blocklist matching uses a **compiled guarded pattern** per term — letter-boundary lookarounds, repeated letters, leetspeak homoglyphs, and separator tolerance for terms of 4+ letters — plus NFKC folding, diacritic folding and a phrase allowlist masked out before matching. Every match must contain at least one real letter. | §3.2 asks for word-boundary matching *and* §6 asks the corpus to defeat spacing, symbol and leetspeak obfuscation. Substring matching satisfies the second and breaks "Scunthorpe"; plain `\b` satisfies the first and loses to "b o m b". The lookaround form does both, and `\b` specifically cannot be used because the leet variants include `$`, `@` and `|`, where `\b` flips meaning. The real-letter rule stops "4 55" being read as a slur. |
| 62 | The **story-side** hard checks are violent *phrases in context*; bare emotive words ("blood", "dead", "gun", "kiss", "monster") are `soft` violations that never fail a story on their own and are instead handed to the Haiku review as things to check. | Calibration against the reference stories, which are the quality bar: the band A shark story contains "a tiny drop of blood", the band C video-games story contains "people who liked shooting things" and "brought video games back from the dead". §4.2's word list plus §4.3's "any hard violation fails" would fail two of the four reference stories. §4.3's model review is where judgement belongs. |
| 63 | A chapter ending in an ellipsis raises a `cliffhanger_marker` check and a **soft** rule 3 violation, and is exempt entirely when the ellipsis follows an all-caps sound effect. | The shark reference ends a band A chapter with "the whole ocean went **WHOOOOSH**..." — a transition, not dread. §4.2's marker rule is a useful signal, but whether a trailing ellipsis is a dread cliffhanger is a judgement; rule 3's real cliffhangers ("it was right behind him") are caught by the hard phrase list regardless. |
| 64 | Rule 7 fires on a branded character **taking part** — acting, speaking, or accompanying the children — not on the name appearing. | §4.1 rule 7 states the boundary itself ("Mario started life as Jumpman" is fine, Mario helping the kids is not), and the video-games reference relies on it: it mentions Mario, Pac-Man and Jumpman factually eight times. Name matching would fail the reference story. |
| 65 | Rule 6 needs a **name plus an identifying detail** (address, phone, workplace, school) before it hard-fails. | "Their teacher, Miss Patel, showed them a map" is an ordinary incidental character; "their neighbour Mrs Atkins of 14 Elm Road" is a real private individual. Deterministically the difference is the identifying detail, so that is what the check looks for. Everything subtler is the Haiku reviewer's call. |
| 66 | The **age band is enforced in code as well as in the classifier prompt**: an `allow_with_care` whose `min_recommended_age` exceeds the youngest child is rewritten to `refuse` / `too_mature_for_band`. | §3.3 asks the classifier to do this itself, but then the Titanic-at-4 behaviour would be a property of one model call. `applyAgeBand()` makes it a property of the system, which is what the corpus asserts. |
| 67 | The classifier's own `parent_message` is **validated before a parent sees it** — no 4-gram echo of the input, no blocklist hit, no injection, no PII, no mention of layers or machinery — and falls back to the template in `config/guardrails/messages.json` otherwise. | §5 forbids echoing the offending text and revealing the layer. That is a hard requirement, and a model-written string cannot be trusted to honour it. The model's version is better copy when it is safe, so it is used when it passes. |
| 68 | An L2 response that fails to validate **fails closed**: refuse, category `other`, template message. Likewise an unparseable safety review returns `safe: false, scary_level: 3`. | §1.3, "fail closed on output, fail kind on input". A parse failure must never become a silent allow. |
| 69 | The L2 classifier constrains its JSON by **prompt instruction plus zod validation**, not `output_config.format`. | Structured outputs are documented as available, but Haiku 4.5's support could not be verified live in this environment and `callModel()` already validates and can repair. A wrong `output_config` shape would 400 on the nightly live run for no benefit. Enabling it is a one-line change once verified — see the note in `lib/guardrails/classify.ts`. |
| 70 | Profanity has no category in the §3.3 enum, so it is logged as `other`. | The enum is a cross-lane contract in `lib/schemas/` and must not be widened without the owner's sign-off. `other` carries it without a schema change. |
| 71 | Prompt files are authored as documents with `## System prompt` / `## Output` / `## User message` sections, and `lib/guardrails/prompts.ts` extracts the model-facing sections. | CLAUDE.md rule 5 wants prompts in `prompts/*.md` with a version header; a reviewable prompt needs rationale that must not be sent to the model. Extraction keeps both, and the bytes sent stay stable so prompt caching still hits. |
## 2026-09-27 — Phase 1, lane 1 (F2, F3, F11 server side)

| # | Decision | Why |
|---|---|---|
| 88 | **Account deletion is one `delete from families`**, leaning on the `on delete cascade` foreign keys, not a stored procedure and not a sequence of deletes. | One statement is one transaction by definition, which is exactly what the F2 AC asks for. Referential actions are run by the system and are not filtered by RLS, so the cascade is complete even though the caller can only see its own rows. `generation_logs.family_id` / `guardrail_events.family_id` are `on delete set null`, so the cost history is anonymized by the same statement — verified, not reimplemented. The `auth.users` row is removed afterwards with the service role so "delete my account" is true rather than nearly true. |
| 89 | **Deleting a child leaves `series.child_ids` untouched.** The stale uuid stays, and the series becomes unreachable rather than broken. | `child_ids` is a `uuid[]` with no foreign key, so nothing cascades. Rewriting it would silently redefine what a series *is*: §3 keys a series on the exact set of children, so "Milo + Juno" minus Juno is a different cast and therefore a different series, not a shrunken one. Past stories stay readable (they are immutable records), the bible stays attached to its series, and a new story about Milo alone starts its own series because `child_key` is derived from the children actually selected. The DELETE endpoint returns `affected_series` so the UI can say "past stories stay in your library". Nothing needs to refresh: an unreachable series is never generated into again. |
| 90 | `timezone = 'UTC'` is treated as **"never set"**, rather than adding a `timezone_set_at` column. | The timezone is detected in the browser and normally arrives with the family row via a short-lived `st_tz` cookie set on the login page. A parent who opens the magic link in a different browser has no cookie, so the dashboard fills it in once. The only cost of the ambiguity is that a family genuinely in UTC is written back to UTC, which changes nothing — and kickoff rule 7's spirit is fewer columns, not more. |
| 91 | At a **parent-facing API boundary, over-long text is rejected with the schema's message rather than silently truncated** — `first_name`, `notes`, `display_name`. Likes stay capped at 40 characters each. | GUARDRAILS.md §3.2 says "enforce max lengths", and truncation is the right default for a programmatic caller, so `sanitize()` still caps by default and takes `cap: false` at the boundary. But a pre-truncated name can never fail the F3 AC's "name 1–30 chars" server-side check, and shortening someone's child's name without telling them is a worse outcome than "First names can be up to 30 characters." Likes are the exception because a trimmed tag loses nothing and `ChildLike` in the shared contract has no custom message to show instead. |
| 92 | **Rate limit: 30 requests per rolling minute per IP; the 31st gets a 429.** Sliding window in process memory, no new dependency. | F11's VT says "30 requests/min from one IP → 429", which reads two ways; the limit is the number served, so the request that exceeds it is the 31st. In-process memory is correct for one instance and is what the VT exercises; it is NOT shared across instances, so a horizontally scaled deployment multiplies the effective limit by the instance count. `setRateLimitStore()` is the seam for `@upstash/ratelimit`, which F11's scope note ("Vercel/Upstash") anticipates. Rejected requests are not counted, or a client hammering the endpoint would never drain its window. |
| 93 | The rate limit lives in the **proxy (middleware), not in each route**. | A route added by another lane is covered the day it lands, and a flood is turned away before it reaches auth or the database. The trade-off is that it is keyed on `x-forwarded-for`, which is spoofable in local development and set by the platform in production. |
| 94 | `middleware.ts` renamed to **`proxy.ts`** (`export default async function proxy`). | Next 16 deprecates the `middleware` file convention and prints a build warning pointing at `proxy`. Behaviour is identical; the build is clean. |
| 95 | A route handler that **changes the session must use `supabaseRoute()` and a relative redirect** (`redirectTo()`), never `supabaseServer()` plus `NextResponse.redirect(request.nextUrl.origin)`. | Two bugs, both found by Playwright and both invisible to unit tests. (a) `supabaseServer()` writes cookies through `next/headers`, which does nothing when the handler returns its own `Response` — the session was verified and then discarded. (b) `request.nextUrl.origin` in a route handler resolves to `http://localhost:<port>` whatever host was actually requested, so on 127.0.0.1 the browser was redirected to a *different origin*, and therefore a different cookie jar, and bounced straight back to /login. A relative `Location` is resolved against the URL the browser asked for and cannot be wrong. |
| 96 | **Google OAuth is wired up but ships disabled**, behind `NEXT_PUBLIC_GOOGLE_OAUTH_ENABLED`. | `supabase/config.toml` has `[auth.external.google] enabled = false` and no credentials, so enabling it is a config change (provider credentials plus the flag), not a code change. The login page says so rather than showing a button that cannot work. |

## 2026-10-02 — refusals keep their reason (issue #24)

| # | Decision | Why |
|---|---|---|
| 159 | **A refusal from the input classifier whose only fault is its minimum age is kept, not replaced by the fail-closed default; and a refusal always shows the owner's pre-written message for its reason, never the classifier's wording.** `salvageRefusal()` overwrites an unusable age and re-validates, for `decision: "refuse"` with a refusal category only - an allow, a self-contradictory reply, or one invalid in any other way still fails closed. A kept reply is logged with one `console.warn` line and carried as `internalReason: 'l2_refusal_age_filled'` on the in-memory result; the `guardrail_events` row has no column for a reason, so it is not stored there. `parentMessageFor()` returns the `config/guardrails/messages.json` template for every refusal except `too_mature_for_band`, where a checked, gentler-angle message from the classifier is still used. `lib/schemas/guardrail.ts` and the classifier prompt are unchanged. | Found in production on the first day: the classifier answers `min_recommended_age: null` when it declines a topic, the contract wants an integer, and so every specific refusal was flattened to `other` with the vaguest message, and logged that way. Keeping the reason immediately exposed the second problem: asked why it declined, the model names the thing it declined ("X is a branded character"), which GUARDRAILS s5 forbids. Not showing model wording for a refusal is the only rule that cannot leak, and the owner's templates are better copy anyway. |

Few stories need these rules, and the cached block stays byte-identical for all of them. The block is our text; the names sit beside it as escaped data, tidied by the schema to at most three short plain names. |

## 2026-10-06 — a rejected fact pack is not forever (issue #28)

| # | Decision | Why |
|---|---|---|
| 171 | **The fact-pack reviewer (prompt v2) judges a pack on its facts, and never on sources it was told not to have.** A knowledge-written pack (#139) has `sources: []` by design; the v1 prompt still opened with "missing sources" as a structural check and the model rejected the first such pack it met for exactly that. | The two halves of #139 contradicted each other: the writer was told to cite nothing, the reviewer to distrust nothing cited. The first new topic after launch ("how animals climb walls") died on it. |
| 172 | **A rejected knowledge pack is researched before the topic is rejected.** `getOrBuildFactPack` runs the build once more with `forceResearch` (the #137 parallel path, with sources) and reviews that; only a second rejection marks the row `rejected`, with both attempts' reasons. One extra build, never a loop. | The second try is a different path, not the same call again. Cost is bounded at one research build (≈ $0.45) per topic per rejection. |
| 173 | **A rejection expires - a day after the first, a week after the second, and the third is final** (`REJECTION_WINDOWS_MS`; the count lives in `content.rejections`). After the window the next request takes the row over (compare-and-swap on `status` and the `updated_at` it read, so two simultaneous requests still make one build) and rebuilds; a waiter that sees an expired rejection keeps waiting for the row it becomes, and a waiter whose builder gave up is told at once. If the research retry itself cannot run (a search outage), the first rejection is still recorded, so an outage never becomes a knowledge call per request. Inside the window the answer is still "we couldn't make a story tonight", free. | A topic could be dead for every family forever on one model judgement; but a topic that is really unwritable must not be re-researched every day for as long as anyone asks (the `/code-review` pass caught both). Three strikes bounds it at three builds, ever - and a takeover build that throws puts the old rejection back rather than deleting the row, or a transient error would reset the count. A transient failure during the research retry (a 529 on the build or on its review) counts as a strike: parking without counting would let an outage keep a borderline topic retrying for ever, and the next window gives it another go. Timing trade-off, noted: a retried build is two builds and two reviews behind one lock, inside the route's 300 s; a waiter can get its pack late and then run out of time writing the story. Accepted for now (a rejected knowledge pack is the rare case); the fix if it bites is a deadline passed through `signal`. The `updated_at` trigger cannot be aged in a test, so the windows are the seam. |

## 2026-10-06 — every parent gets a book (issue #32)

| # | Decision | Why |
|---|---|---|
| 176 | **Owner's metric: every customer gets a book, every time, without much added latency.** Delivery is the headline number; quality is measured second. The design is a ladder (issue #32): never discard, degrade - length, polish and at the floor the topic give way; the fourteen hard rules never do. | The eval and production both showed parents getting nothing: a truncated write, two safety breaches, a rejected pack, a dead API. Each is a bedtime with no story. |
| 177 | **Rung 0: the writer's cap is 64,000 output tokens, and the story's own size is a named bound (`WRITER_STORY_TOKENS_MAX`, 12,000) that the cap must clear by more than 50,000; the generation route's `maxDuration` rises from 300 s to 660 s to match** (the project runs Vercel Fluid compute, ceiling 800 s; a write at the 6 Oct rate of ~32,000 tokens per 300 s needs the room, or Vercel kills it before the cap matters - `test/unit/deploy-config.test.ts` ties the two).** 32,000 was never a hard rule (#134: a cap, not a cost); Sonnet 5 allows 128,000. The thinking is adaptive and unbounded; the story is not. A hard ceiling, if ever wanted, is the model's `effort` setting for the longest stories - a quality trade the owner has not asked for. | A 15-minute band-C story hit 32,000 twice on 6 Oct (≈ 6,500 tokens of story under 25,000 of thinking) and the parent got no book, at full cost. |
| 178 | **Rungs 1 and 2: a story that breaks a hard rule is mended, then cut, before it is ever discarded.** The gate knows the rule and the quote. Rung 1 (`lib/generate/mend.ts`, prompt `mend.v1`, purpose `mend`): one helper call rewrites only the sentences holding the quotes - the model may change nothing it was not given, and an edit it cannot place is dropped - then the full gate runs again. It also replaces the two-minute full rewrite when attempt 1 failed *only* on hard-rule breaches (`onlyHardRuleBreaches`). Rung 2 (`cutViolations`): if a breach survives, the sentences holding the quotes are removed, the free scan confirms, and the story ships `flagged` with the existing banner. A cut counts only when every hard violation was placed and every passage removed, and the cut story goes through the whole gate again (safety review included) before it ships, flagged; an in-place mend is regated as attempt 1, so the full rewrite still follows if the mend did not clear the breach. A breach that survives everything - a quote the text does not contain, a chapter that would be emptied - is the one discard left. What was done is saved as `quality.mended`, for the text that shipped only. GUARDRAILS.md §4.1 is reworded to this ladder; it is a loosening of the discard rule, approved by the owner with the #32 design ("approved", 2026-10-06), and the fourteen rules themselves are untouched. | Two full writes and then nothing was the worst outcome in the product, and it happened three times in two eval runs. Mending costs ~10 s and ~$0.01; it never relaxes a rule, because the gate runs again on what it produced and the cut is confirmed by the scanner that found the breach. |
| 179 | **Rung 3: an unusable first write is retried once, one length tier shorter (15 → 10 → 5; 5 stays 5), and that story is the one saved.** Unusable means the parse and the one repair both failed - a cut-off response, a structurally short story. The retry is the second and last writing call: it is not streamed (the client already holds attempt 1's chapters; the story arrives in `done`, as a rewrite does, and the reader now takes its title from `done`), its gate verdict is final (attempt 2 - a breach goes down the mend/cut ladder), the story row records the length actually written, and `quality.first_attempt` says why (`output unusable; retried 10 -> 5 minutes`). No schema change. | A shorter story fits every cap and fails far less; the parent who asked for fifteen minutes gets ten tonight instead of none. Latency: one non-streamed write (~60–90 s for 10 minutes) on a path that used to end in "we couldn't make a story". The retry starts only with `RETRY_MIN_MS` (150 s) left before the request deadline the route passes in (`deadlineMs`), and its timeout is bounded by the time left: a retry the platform cuts off sends the parent nothing, not even an error. For that room after a write cut off at the cap (~600 s), the route's `maxDuration` rises to 800 s, Vercel Pro's Fluid ceiling; a test ties the three numbers together. The retry is one attempt (`maxRetries: 0`; callModel's retries would each get the full timeout), its timeout is measured at the moment of each call, and near the deadline (`MEND_MIN_MS`, 40 s) the ladder cuts instead of mending. It is logged as `purpose: 'rewrite'` - a separate purpose would be a schema and migration change for a cost split nobody reads yet; `quality.first_attempt` tells the two apart per story. |
| 180 | **Rung 4: when the writer is unreachable - a 5xx, 429 or overloaded stream (`writerUnavailable`) - the story is written once, not streamed, by the fallback writer (`config/models.json` role `writer_fallback` = Haiku 4.5, the owner's decision of 2026-10-06), and that is the book.** It is the second and last writing call: its gate is final and a breach goes down the mend/cut ladder; it respects the request deadline and makes one attempt. Not a fallback: a 400 (bad request, or an exhausted balance - the fallback would fail the same way), an auth error, a refusal. Recorded in `quality.first_attempt` (`writer unavailable (status 529); written by …`). Test seam: a fixture can now replay a failure (`error: {status, message}`), only ever written by tests. A bake-off run (`writingModel` set) never falls back, so a contestant is never scored on another model's story. And on every path where the stream gave no title (the fallback, an unusable first write), `meta` - the story id, topic and content notice the reader needs - is sent from the finished story before `done` (from `/code-review`). | A parent should not lose the night to an Anthropic overload. Haiku is fast and already priced; its stories are shorter on craft, which the gate and the banner handle. The 2026-10-07 models fetch shows Sonnet 5.5 and Haiku 5.5 now current and Sonnet 5 / Haiku 4.5 legacy; whether to move any role is the owner's decision and is not made here. |
